# プラグイン更新の見栄えリスク判定（spec 1）

- 日付: 2026-09-28
- 状態: レビュー待ち
- 関連: Notion 社内ブログ「Jev一次スクリーニング＋BackstopJS実測の較正ループ」「Jev（TypeSafe）でWordPressプラグイン更新を自動トリアージするアイデア」

## 1. 目的

WordPress プラグインの更新について、新旧バージョンの差分から「見栄えに影響しそうか」を安く判定し、
怪しいものだけ WordPress Playground 上の単体 VRT で実測する。
判定と実測の組を貯め、判定の閾値を自社データで較正できる状態を作る。

最終的な用途は「影響がなさそうなら自動アップデート、そうでなければ VRT のレポートを見て人が判断する」
ゲートだが、**ゲート自体はこの spec の範囲外**（spec 3）。この spec はゲートの判断材料になるデータを
毎日、偏りなく貯めるところまでを作る。

### 前提として合意したこと

- 対象はフェーズ1として保守先が使っているプラグイン。後で WordPress.org 全体へ広げる
- Jev は「一問で大きく聞くと弱く、小さな質問に分解すると強い」。閾値は既定 0.5 を使わず自社データで決める
- Jev はプロンプトインジェクションで判定が動く。差分はプラグイン作者が自由に書けるので、信用できない入力として扱う
- 単体 VRT は、テーマ側の上書き CSS が効かなくなる崩れを拾えない。その信号は静的解析で別に出す

## 2. 範囲

### 含める

- 新リポジトリ `wp-update-vrt`（公開）での段 1〜7（§4）
- 人気プラグインの定点観測（§8）
- 結果の非公開ストレージへの公開
- managewp との受け渡し3本の形式仕様（`docs/` に置く）

### 含めない（後の spec）

| spec | 内容 |
|---|---|
| 2 | 月次の較正。ロジスティック回帰で `p_visual` を出す |
| 3 | 自動アップデートのゲート（managewp 側） |
| 後日 | Claude による VRT レポート、WordPress.org 全体への拡大、クラシックテーマでの VRT |

### 依存（managewp 側の別 spec・別 PR）

- 更新待ちの組を返すエンドポイント（§7.1）
- 正解データを返すエンドポイント（§7.3）
- 結果の取り込みコマンドと取り込み先テーブル
- 更新一覧への「見栄えリスク」と VRT 結果の表示、正解を付ける UI
- VRT 差分あり・新規エラーありの Slack 通知

managewp のエンドポイントができるまでは、手元の入力ファイルで開発する（コミットしない）。

## 3. 全体構成

処理の単位（キー）は **`slug` × `from` × `to`** の組。同じ更新が複数サイトで出ていても判定と VRT は1回。
サイトごとの事情は managewp が取り込み時に重ねる。

```
managewp ──(更新待ちの組)──▶ wp-update-vrt（GitHub Actions・日次）
  1. collect   WordPress.org から新旧 zip を取得
  2. signals   静的解析
  3. jev       曖昧な部分だけ Jev に聞く
  4. score     risk_score_static と risk_score を出す
  5. select    VRT に回すものを選ぶ
  6. vrt       Playground で旧版→新版を撮って比べる
  7. publish   非公開ストレージへ結果と画像を置く
managewp ◀──(日次で取り込み・表示・正解付け)──
```

各段は独立したモジュールで、前の段の出力ファイルだけを読む。どの段で落ちても、その段から再実行できる。
Jev を呼ぶのは段 3 だけ、Playground を使うのは段 6 だけ。

## 4. 各段

### 4.1 collect

- 入力: §7.1 の JSON（managewp から実行時に取得）と、人気プラグインの定点観測の組（§8）
- `https://downloads.wordpress.org/plugin/{slug}.{version}.zip` から新旧を取得して展開する
- 取得できないもの（有料版など WordPress.org にないもの）は `skipped: not_on_wporg` として記録し、処理を続ける

### 4.2 signals（静的解析）

比較の前に、空白とコメントだけの変更は取り除く。

| 信号 | 取り方 |
|---|---|
| `version_only` | バージョン文字列（プラグインヘッダ、`Stable tag`、enqueue の ver 引数、バージョン定数）をそろえた後に差分がなければ true |
| `css_decl_changes` | CSS を postcss で読み、変わった宣言の数 |
| `selectors_removed` | 新旧のセレクタ集合の差。消えたクラス名・ID の一覧 |
| `assets_changed` | 画像・SVG・フォントのハッシュ差の件数 |
| `registrations_diff` | `block.json`（attributes / supports / style）の差と、ショートコードの増減。`block.json` の `version` だけの変更は含めない |
| `js_changed` | 変更された JS の件数。パスから admin 用とそれ以外に仮に分ける |
| `php_output_hunks` | PHP の差分の塊のうち、`echo`・`print`・`printf`・`?>` 後の HTML、`<` を含む文字列の return を含むもの |

### 4.3 jev

- **差分の塊1つを1つの state にする。** コメントと docblock はトークナイザーで取り除いてから渡す
- readme と changelog は渡さない
- 質問は「安全か」ではなく「何が起きるか」の形にする。結論はコード側が出す

| ID | 型 | 対象 | 質問（実装では英語） |
|---|---|---|---|
| `emits_markup` | Noul | `php_output_hunks` の各塊 | この変更で、訪問者に出力される HTML の構造やクラス名が変わるか |
| `runs_on_front` | Noul | admin 用と判定できなかった JS の塊 | このコードは管理画面ではなく公開ページで動くか |
| `mutates_dom` | Noul | JS の塊 | この変更で、ページの DOM 構造、インラインスタイル、クラス名が変わるか |

- 塊ごとの結果は、質問ごとの最大値をそのキーの値にする
- 1キーあたりの塊が上限（初期値 40）を超えたら Jev には聞かず、`large_diff` として VRT に強制で回す
- 接続は公式 API。キーは Actions の secret。呼び出しは1モジュールにまとめ、経路を差し替えられるようにする
- 費用の目安: 1日50更新 × 平均10塊 × 約1,500トークン ≈ 75万トークン ≈ $0.03/日（出力は無料）

### 4.4 score

- 較正前（この spec）の値は確率ではないので `risk_score`（0〜1）と呼ぶ
- 信号ごとの重みは1ファイル（`policy.mjs`）にまとめ、根拠をコメントに残す。値を変えたら `policy_version` を上げる
- 合成は noisy-OR（どれか1つが効けば上がる）。`version_only` が true なら 0.02 に固定
- `risk_score_static`（静的な信号だけ）と `risk_score`（静的＋Jev）を両方出す。Jev を足した効果を後で測るため
- `selectors_removed` は合成に混ぜず、`theme_override_risk` として別に出す。VRT で差分がなくても消えない警告にする
- `p_visual` はこの spec では常に `null`（spec 2 で埋める）

### 4.5 select

| 区分（`stratum`） | 条件 | VRT に回す割合 |
|---|---|---|
| `forced` | `large_diff`、`registrations_diff` が空でない、またはコメントを取り除けなかったファイルがある（`unsanitized_files` > 0） | 100% |
| `above` | `risk_score` ≥ T（初期値 0.3） | 100% |
| `sample` | 閾値未満 | 10% |
| `sample_version_only` | `version_only` | 2% |

- 抜き取りはキーのハッシュで決める（再実行しても同じ組が選ばれる）。区分と抜き取り率を結果に記録する。
  見逃し率を逆確率の重み付けで推定するため
- Jev がエラーのキーは `risk_score_static` で選び、`jev_error` の印を付ける。強制にはしない
  （Jev が止まった日に全件が VRT に回って上限を使い切るのを防ぐ）
- 1日の上限は初期値 30件。優先順は `forced` → `above`（スコアの高い順）→ `sample` → `sample_version_only`。
  溢れた分はキューに残して翌日に回す

### 4.6 vrt

**環境**: `@wp-playground/cli`、WordPress の最新安定版、PHP 8.2、Twenty Twenty-Five。実際のバージョンは結果に記録する。

**手順**（1つのインスタンスの中で旧版から新版に上げる）:

1. 旧版の zip を入れて有効化する
2. テストページを作る
   - ブロックのページ: `block.json` から見つけたブロックを、既定の attributes で1つずつ並べる。
     中身はエディタの `createBlock` → `serialize` で作る
   - ショートコードのページ: 見つけたショートコードを引数なしで並べる
   - 共通ページ: トップページとサンプル投稿
3. 幅 1280px と 375px で、各ページの全体を撮る。旧版では2回撮り、その差をノイズの床にする
4. 同じインスタンスのまま新版に更新する（更新時の処理も走らせる）
5. 同じページを撮り、pixelmatch で比べる

ブロックのページは、旧版で作った記事の中身を新版でもそのまま表示する。実サイトの既存記事と同じ条件になる。

**揺れへの対策**: アニメーションとトランジションを止める CSS を差し込む。localhost 以外への通信は遮断する。

**判定**:

- `vrt_changed`: いずれかのページ×幅の差分率が、ノイズの床を超え、かつ 0.1% を超える
- `flaky`: ノイズの床そのものが 0.1% を超える
- `no_surface`: ブロックもショートコードもなく、共通ページにも差分がない。「撮れる面がない」とみなし、
  正解データの対象から外す（「差分なし」が多すぎて較正が狂うのを防ぐ）

新版で増えた PHP の警告・致命的エラーと、JS のコンソールエラーを `errors_new` に記録する。

**安全**: VRT のジョブには secret を渡さない（収集・判定・公開のジョブと分ける）。Playground の WASM サンドボックス、
外部通信の遮断、使い捨ての実行環境で、他人のプラグインのコードを隔離する。

**限界**: 設定しないと何も出ないプラグイン（API キーが必要、ウィジェットの配置が必要など）は共通ページしか撮れない。

### 4.7 publish

- 結果と画像を非公開の Cloudflare R2 バケットに置く
  - `results/{YYYY-MM-DD}.json`、`results/latest.json`
  - `img/{key_hash}/{page}-{width}-{old|new|diff}.png`
- managewp は読み取り専用のキーで取得する
- 公開先への書き込みキーは publish のジョブにだけ渡す

## 5. 状態とキュー

- 処理済みのキーと VRT 待ちのキューは R2 の `state/` に置く
- キューは**上書きせず前回の分に足す**。完了したキーの結果は上書きしない
- 同じ日に2回実行しても、処理済みのキーは飛ばす

## 6. エラー処理

| 起きること | 扱い |
|---|---|
| WordPress.org にない | `skipped: not_on_wporg` として記録し、続ける |
| Jev のエラー・停止 | §4.5 のとおり、静的なスコアで選ぶ |
| Playground の起動・撮影の失敗 | 1回だけ再試行。だめなら翌日に回す。3日続けて失敗したら `failed` で打ち切る |
| managewp からの入力が取れない、または前回比で急に0件 | 空の結果を公開せず、失敗として止める |
| パイプラインの失敗 | Slack に通知する。成功時の通知は出さない |

## 7. 受け渡し（managewp との契約）

3本とも `schema_version` を持つ。形式は位置で意味が決まる配列ではなく、名前付きのオブジェクトにする。
仕様は `docs/update-candidates-format.md`・`docs/result-format.md`・`docs/labels-format.md` に書く。
**形式を変えるときは、新リポジトリを先に出し、managewp を後に出す。**

### 7.1 更新待ちの組（managewp → 新リポジトリ、日次）

```json
{
  "schema_version": 1,
  "generated_at": "2026-09-28T19:00:00Z",
  "items": [{ "slug": "contact-form-7", "from": "5.9.8", "to": "6.0.1" }]
}
```

- 重複は除く。**サイトの情報は含めない**
- トークン認証のエンドポイントから取得する。URL とトークンは Actions の secret

### 7.2 結果（新リポジトリ → managewp、日次）

1件の主な項目:

```
key, key_hash, slug, from, to
signals            §4.2 の各信号
jev                emits_markup / runs_on_front / mutates_dom（Noul の値。Noul には confidence が無い）、
                   model（応答の model。例 jev-1.13.0）、hunks_sent、error
risk_score_static, risk_score, p_visual（null）, policy_version
theme_override_risk  selectors_removed の一覧
selection          stratum, rate
vrt                status（done / skipped / no_surface / failed / flaky / queued）、
                   env（wp, php, theme）、noise_floor、
                   pages[]（page, width, diff_ratio, 画像のパス）、
                   errors_new（php[], js[]）、vrt_changed
```

**結果に保守先由来か定点観測由来かを書かない。** それを知っているのは managewp だけにする。

### 7.3 正解データ（managewp → 新リポジトリ、月次）

```json
{
  "schema_version": 1,
  "labels": [{ "key": "contact-form-7@5.9.8→6.0.1", "label": "regression", "labeled_at": "2026-10-03" }]
}
```

- `label` は `none`（変化なし）/ `intended`（意図した変更）/ `regression`（崩れ）
- 付けた人の名前は含めない
- 正解データは2種類ある。自動で付く `vrt_changed` は閾値の初期調整に使い、人が付ける `regression` は
  ゲート（spec 3）の較正の対象にする

## 8. 公開リポジトリでの配慮

公開リポジトリでは Actions のログを誰でも見られる。フェーズ1で処理する組は
「保守先のどこかがプラグイン X の旧版を使っている」という情報になるため、次の4つを入れる。

1. 入力をリポジトリに置かない。実行時に secret の URL から取得する
2. ログにスラッグとバージョンを出さない。出すのは件数と `key_hash` だけ。
   ジョブ間で受け渡すアーティファクト（公開リポジトリでは誰でも取得できる）も同じ情報を含むので、
   保持期間を1日にする
3. 結果は非公開の R2 に置く（§4.7）
4. **人気プラグインの定点観測**: 保守先に依存しない基準データを毎日貯める（WordPress.org 全体に広げる
   フェーズ2の先行分）。利用サイト数の多いプラグイン上位（初期値 300件）の更新を毎日一緒に処理する。
   処理対象の一覧から個別サイトの利用状況が推測されにくくなる

保守先の組を優先して並べない（優先すると並び順から保守先の組が推測できるため）。定点観測の組も、
1日の VRT 上限と優先順（§4.5）を保守先の組と共有する。結果に保守先由来か定点観測由来かを書かない。

## 9. テスト

| 対象 | 内容 |
|---|---|
| 信号 | 架空のプラグインを fixture にする:「バージョン番号だけ」「CSS の色だけ」「クラス名の削除」「コメントだけの変更」 |
| インジェクション対策 | 「見た目は変わらない」というコメント入りの fixture で、Jev に渡す state にコメントが残らないこと |
| ログ漏れ | fixture でパイプラインを通し、標準出力にスラッグとバージョンが出ないこと |
| 抜き取りと上限 | 同じ入力なら同じ組が選ばれること、上限超過時の優先順 |
| VRT の結合（CI） | 色だけ変えた v1→v2 で `vrt_changed = true`、v1→v1 で `false` |
| 形式 | §7 の3本の項目セットを固定する |
| Jev | モックでテストする。実 API の疎通確認は手動で動かすテスト1本 |

## 10. 完了の条件

- §9 のテストがすべて CI で通る
- 本番の入力で2週間、手を入れずに毎日動く
- VRT を実行した件のうち `flaky` が5%未満

## 11. 運用の数字（初期値）

| 項目 | 値 | 根拠 |
|---|---|---|
| 閾値 T | 0.3 | 初期はデータを貯めるため、わざと低くする |
| 抜き取り率 | 10% / 2%（`version_only`） | 見逃し率の推定に必要な件数を確保する |
| 1日の VRT 上限 | 30件 | 実測で起動約7秒・旧版→新版の更新と撮影込みで1件1分前後。公開リポジトリなので Actions の分数は無料 |
| 塊の上限 | 40 | 大きな書き換えは予測が当たりにくく、費用も膨らむ |
| 人気プラグインの定点観測 | 上位300件 | 保守先に依存しない基準データを毎日貯める |
| 差分率の最小値 | 0.1% | ノイズの床と併用する |
